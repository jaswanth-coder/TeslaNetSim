Network simulation is fundamentally about validating protocols, queuing algorithms, and physical channel dynamics in software before committing to expensive silicon fabrication or physical deployments. Among modern discrete-event simulators, ns-3 stands out because it is written entirely in high-performance C++ and avoids the synthetic scripting layer abstraction (like OTcl in ns-2) in favor of direct, object-oriented software engineering.

This document is a rigorous, self-contained reference designed for independent learners and researchers. It bridges the gap between high-level conceptual networking and the low-level memory, scheduling, and protocol aggregation mechanics that govern every ns-3 execution.

1. Introduction & Theoretical Foundations

1.1 The Discrete-Event Simulation (DES) Paradigm

Unlike real-time hardware emulators or game engines that continuously increment time in synchronized clock ticks ($\Delta t = 16.6\text{ ms}$ for 60 FPS), ns-3 is a Discrete-Event Simulator (DES). In a DES model, the state of the network changes only at distinct instants in time called events.

The core of the simulator is an Event Calendar, mathematically represented as a priority queue $Q$ ordered strictly by the event execution timestamp $t_e$:

\[ Q = \{(t_1, f_1), (t_2, f_2), \dots, (t_n, f_n)\} \quad \text{where } t_1 \le t_2 \le \dots \le t_n \]

Each tuple $(t_i, f_i)$ represents a scheduled function callback $f_i$ to be invoked at virtual simulation time $t_i$. When an event executes, it may alter protocol states and insert zero or more new events into $Q$ (for example, scheduling a packet reception event at $t_{\text{rx}} = t_{\text{tx}} + \text{propagation delay}$).

1.2 Virtual Time vs. Wall-Clock Stopwatch Time

A fundamental mental leap required when learning ns-3 is distinguishing between Simulation Time (Virtual Time) and Real-World Wall-Clock Time:

  • Simulation Time: The theoretical timeline of the modeled network world (stored as a 64-bit integer tracking nanoseconds or picoseconds).

  • Wall-Clock Time: The physical elapsed seconds measured by the CPU executing machine instructions on your computer.

Because the simulation clock only updates when the scheduler dequeues the next event from $Q$, no CPU time is wasted simulating intervals of complete inactivity. If event $e_1$ executes at virtual time $t = 1.0\text{ s}$ and the very next event $e_2$ is scheduled at virtual time $t = 100.0\text{ s}$, the scheduler instantaneously leaps the clock forward by $99.0\text{ s}$ in a single CPU instruction.

Important
 If you write Simulator::Stop(Seconds(600.0)); Simulator::Run(); without installing applications or scheduling packets, the simulator priority queue contains only the stop event. The engine executes it immediately, and the simulation completes in less than 2 milliseconds of real wall-clock time!

1.3 Simulator State Machine: Run, Stop, and Destroy

The execution of an ns-3 program is controlled by static methods of the Simulator class:

  • Simulator::Schedule(Time const &time, MEM mem_ptr, OBJ obj): Inserts an event into the priority calendar.

  • Simulator::Run(): Hands control of the main thread over to the event loop. The scheduler pulls the head of the event queue and invokes callbacks until either the queue is empty, Simulator::Stop() is triggered, or a fatal assertion occurs.

  • Simulator::Stop(Time const &time): Schedules an explicit terminal event that forces Run() to break its while-loop.

  • Simulator::Destroy(): Iterates through all registered singletons, clears the event list, and breaks circular reference chains between objects.

2. Simulator Core Object Architecture & Memory Model

2.1 The Peril of Manual Memory Management (new / delete)

In standard C++, dynamically allocating network objects with raw heap pointers creates immense risk:

// ❌ INCORRECT & DANGEROUS IN NS-3
Node* n = new Node();
PointToPointNetDevice* dev = new PointToPointNetDevice();
n->AddDevice(dev);
// Who owns 'dev'? If 'n' is deleted, does 'dev' leak? 
// If 'dev' is deleted first, does 'n' hold a dangling pointer?

In large-scale simulations containing millions of packets and thousands of transient routing table entries, manual deallocation leads inevitably to double-free panics, memory exhaustion, or catastrophic segmentation faults.

2.2 Intrusive Reference Counting with Ptr<T>

To provide automatic, leak-free memory management without the CPU overhead of a non-deterministic garbage collector, ns-3 implements intrusive reference counting via the base class SimpleRefCount<T> and the template smart pointer Ptr<T>.

Every fundamental object in ns-3 (such as Node, NetDevice, Channel, Packet) inherits from Object, which inherits from SimpleRefCount. An internal 32-bit counter tracks how many active Ptr<T> references currently point to that object:

// ✅ THE CANONICAL NS-3 IDIOM
Ptr<Node> node = CreateObject<Node>(); // Ref count = 1

{
  Ptr<Node> alias = node;              // Ref count = 2
}                                      // 'alias' goes out of scope -> Ref count = 1

node = nullptr;                        // Ref count = 0 -> Destructor runs automatically!
Tip
 Always instantiate ns-3 objects using CreateObject<T>() or Create<T>(). Never use the raw new operator on classes derived from ns3::Object.

2.3 Object Aggregation and Querying (GetObject)

Unlike monolithic architectures where a host object contains rigid member variables for every protocol, ns-3 uses an Object Aggregation System. A Node begins its life completely bare. When you install an IPv4 stack, ns-3 aggregates an Ipv4 protocol object into the node's internal component list.

Any module can subsequently query the node at runtime to obtain a reference to that aggregated protocol:

Ptr<Node> n = CreateObject<Node>();
// Query if Node n has an IPv4 protocol engine installed:
Ptr<Ipv4> ipv4 = n->GetObject<Ipv4>();

if (ipv4 == nullptr) {
  // Evaluates to TRUE because no stack has been installed yet!
}

3. The Canonical 7-Step Simulation Recipe

3.1 Pipeline Overview & Structural Table

Regardless of whether you are configuring a simple point-to-point serial line or an advanced multi-link IEEE 802.11be WiFi 7 infrastructure, all simulation scripts follow seven sequential phases:

Step Phase Primary Helpers & Classes Underlying Architectural Action
1 CLI Argument Parsing CommandLine cmd; Binds terminal arguments to local C++ variables dynamically.
2 Node Creation NodeContainer nodes; Instantiates bare Ptr<Node> hosts with empty aggregation registries.
3 Device & Channel Setup PointToPointHelper, WifiHelper Allocates physical links (Layer 1) and installs NICs (Layer 2) on hosts.
4 Protocol Stack Installation InternetStackHelper stack; Aggregates ARP, IPv4/IPv6, ICMP, TCP, and UDP to each node.
5 IP Address Assignment Ipv4AddressHelper address; Constructs Ipv4Interface objects and assigns IP/subnet masks.
6 Application Scheduling UdpEchoServerHelper, OnOffHelper Binds socket listeners and schedules packet transmission events.
7 Execution & Teardown Simulator::Run(), Simulator::Destroy() Drives the discrete-event calendar and clears cyclic memory graphs.

3.2 Step 1: CommandLine Argument Parsing

Hardcoding configuration parameters (e.g. data rate, packet size, number of stations) directly into source code forces a full recompilation whenever a variable changes. CommandLine binds variables directly to shell parameters:

uint32_t nPackets = 10;
CommandLine cmd(__FILE__);
cmd.AddValue("nPackets", "Number of UDP packets to transmit", nPackets);
cmd.Parse(argc, argv);

3.3 Step 2: NodeContainer & Virtual Hosts

The NodeContainer helper simplifies batch operations across groups of nodes:

NodeContainer nodes;
nodes.Create(2); // Instantiates nodes.Get(0) and nodes.Get(1)

3.4 Step 3: Medium Channels & NetDevices

A NetDevice models the Network Interface Card (NIC), while a Channel models the transmission medium connecting them:

PointToPointHelper p2p;
p2p.SetDeviceAttribute("DataRate", StringValue("5Mbps"));
p2p.SetChannelAttribute("Delay", StringValue("2ms"));

NetDeviceContainer devices = p2p.Install(nodes);

3.5 Step 4: Layer 3 Internet Protocol Stack

The InternetStackHelper aggregates the Layer 3 and Layer 4 protocol engines to each node in the container:

InternetStackHelper stack;
stack.Install(nodes);

3.6 Step 5: IP Addressing & Subnet Interfaces

Once the internet stack is installed, IP addresses are allocated and bound to the devices:

Ipv4AddressHelper address;
address.SetBase("10.1.1.0", "255.255.255.0");
Ipv4InterfaceContainer interfaces = address.Assign(devices);
// interfaces.GetAddress(0) -> 10.1.1.1
// interfaces.GetAddress(1) -> 10.1.1.2

3.7 Step 6: Application Sockets & Traffic Scheduling

Applications generate traffic over sockets. Here, a server listens on port 9, and a client transmits three echo requests:

UdpEchoServerHelper echoServer(9);
ApplicationContainer serverApps = echoServer.Install(nodes.Get(1));
serverApps.Start(Seconds(1.0));
serverApps.Stop(Seconds(10.0));

UdpEchoClientHelper echoClient(interfaces.GetAddress(1), 9);
echoClient.SetAttribute("MaxPackets", UintegerValue(3));
echoClient.SetAttribute("Interval", TimeValue(Seconds(1.0)));
echoClient.SetAttribute("PacketSize", UintegerValue(1024));

ApplicationContainer clientApps = echoClient.Install(nodes.Get(0));
clientApps.Start(Seconds(2.0));
clientApps.Stop(Seconds(10.0));

3.8 Step 7: Scheduler Execution & Teardown

The simulation loop begins running. Once all events finish or simulation time reaches the stop point, memory cleanup occurs:

Simulator::Run();
Simulator::Destroy();

3.9 Complete Canonical Implementation (first.cc)

The complete, standalone C++ source code integrating all 7 steps into an executable simulation:

#include "ns3/core-module.h"
#include "ns3/network-module.h"
#include "ns3/internet-module.h"
#include "ns3/point-to-point-module.h"
#include "ns3/applications-module.h"

using namespace ns3;

NS_LOG_COMPONENT_DEFINE("CanonicalFirstScript");

int main(int argc, char* argv[])
{
  // ----------------------------------------------------
  // STEP 1: Command Line Parsing
  // ----------------------------------------------------
  CommandLine cmd(__FILE__);
  cmd.Parse(argc, argv);

  Time::SetResolution(Time::NS);
  LogComponentEnable("UdpEchoClientApplication", LOG_LEVEL_INFO);
  LogComponentEnable("UdpEchoServerApplication", LOG_LEVEL_INFO);

  // ----------------------------------------------------
  // STEP 2: Node Creation
  // ----------------------------------------------------
  NodeContainer nodes;
  nodes.Create(2);

  // ----------------------------------------------------
  // STEP 3: Channel and NetDevice Setup
  // ----------------------------------------------------
  PointToPointHelper pointToPoint;
  pointToPoint.SetDeviceAttribute("DataRate", StringValue("5Mbps"));
  pointToPoint.SetChannelAttribute("Delay", StringValue("2ms"));

  NetDeviceContainer devices;
  devices = pointToPoint.Install(nodes);

  // ----------------------------------------------------
  // STEP 4: Install Internet Protocol Stack
  // ----------------------------------------------------
  InternetStackHelper stack;
  stack.Install(nodes);

  // ----------------------------------------------------
  // STEP 5: Assign IP Addresses
  // ----------------------------------------------------
  Ipv4AddressHelper address;
  address.SetBase("10.1.1.0", "255.255.255.0");

  Ipv4InterfaceContainer interfaces = address.Assign(devices);

  // ----------------------------------------------------
  // STEP 6: Install Applications
  // ----------------------------------------------------
  UdpEchoServerHelper echoServer(9);
  ApplicationContainer serverApps = echoServer.Install(nodes.Get(1));
  serverApps.Start(Seconds(1.0));
  serverApps.Stop(Seconds(10.0));

  UdpEchoClientHelper echoClient(interfaces.GetAddress(1), 9);
  echoClient.SetAttribute("MaxPackets", UintegerValue(3));
  echoClient.SetAttribute("Interval", TimeValue(Seconds(1.0)));
  echoClient.SetAttribute("PacketSize", UintegerValue(1024));

  ApplicationContainer clientApps = echoClient.Install(nodes.Get(0));
  clientApps.Start(Seconds(2.0));
  clientApps.Stop(Seconds(10.0));

  // ----------------------------------------------------
  // STEP 7: Run Simulation & Clean Up Memory
  // ----------------------------------------------------
  Simulator::Run();
  Simulator::Destroy();

  return 0;
}

4. Fatal Traps, Assertion Failures & Debugging

4.1 Inverting Steps 4 & 5: The Unbound Ipv4 Protocol Assertion

One of the most frequent errors encountered by beginners is calling Ipv4AddressHelper::Assign() before InternetStackHelper::Install():

// ❌ FATAL RUNTIME ERROR
Ipv4AddressHelper address;
address.SetBase("10.1.1.0", "255.255.255.0");
Ipv4InterfaceContainer interfaces = address.Assign(devices); // CRASH!

InternetStackHelper stack;
stack.Install(nodes);

Underlying Mechanism: address.Assign(devices) iterates over each device, queries the parent node for an aggregated Ipv4 protocol pointer via node->GetObject<Ipv4>(), and attempts to attach an IP interface. Because stack.Install(nodes) has not yet run, node->GetObject<Ipv4>() returns nullptr, triggering a fatal assertion panic in debug mode:

assert failed. cond="ipv4 != 0", msg="Ipv4AddressHelper::Assign(): 
Node 0 does not have an Ipv4 aggregated to it", file=../src/internet/helper/ipv4-address-helper.cc

4.2 Dangling Cyclic References without Simulator::Destroy()

Because ns-3 uses reference counting, circular ownership structures can form during simulation (for instance, an application holds a socket callback which holds a reference back to the host node). If main() terminates without invoking Simulator::Destroy(), these circular references prevent destructors from running, resulting in lingering memory leaks and unwritten log buffers.

4.3 Virtual Time Trap: Instant Termination with No Events

If you forget to call app.Start() or schedule traffic generators, the simulator finds zero events in the priority queue between $t = 0$ and the simulation stop time. The execution will immediately complete in zero wall-clock seconds without transmitting any frames.

5. Build Configurations & Toolchain Mechanics

5.1 Debug Profile vs. Optimized Profile

ns-3 provides two major build profiles orchestrated via the CMake build system:

  • Debug Profile (--build-profile=debug): Compiles with debugging symbols (-g) and activates NS_ASSERT macros. Whenever an illegal pointer, out-of-bounds address, or uninitialized link is accessed, the simulator halts instantly with an informative line number and message. Always develop and write new scripts in debug mode!

  • Optimized Profile (--build-profile=optimized): Disables runtime assertions and compiles with compiler optimizations (-O3). Simulation parameter sweeps, heavy packet generation, and wireless Monte-Carlo runs execute 5x to 10x faster in optimized mode.

# Configure for deep debugging and error catching:
./ns3 configure --build-profile=debug

# Configure for production-speed parameter sweeps:
./ns3 configure --build-profile=optimized

5.2 Dynamic CLI Flags & The ns-3 Attribute System

Any parameter defined as an Attribute in an ns-3 class can be overridden from the command line without modifying the C++ source file:

# Override point-to-point data rate dynamically at runtime:
./ns3 run "scratch/first --ns3::PointToPointNetDevice::DataRate=10Mbps"

5.3 The NS_LOG Logging Subsystem

ns-3 features a granular logging framework that allows inspection of internal packet operations without cluttering standard output:

# Enable full packet exchange logs for the UDP echo client:
export 'NS_LOG=UdpEchoClientApplication=level_all|prefix_time'
./ns3 run scratch/first

6. Packet Tracing, PCAP & NetAnim Visualizer

6.1 Ascii Tracing (AsciiTraceHelper)

Ascii tracing produces a human-readable text log recording every packet enqueue, dequeue, transmission, and drop event with high-precision timestamps:

AsciiTraceHelper ascii;
pointToPoint.EnableAsciiAll(ascii.CreateFileStream("first.tr"));

6.2 PCAP Packet Sniffing (Wireshark Inspection)

ns-3 can capture standard .pcap packet dump files that open directly in Wireshark or tcpdump:

pointToPoint.EnablePcapAll("first");

This generates files such as first-0-0.pcap and first-1-0.pcap. You can inspect protocol headers, sequence numbers, checksums, and timing jitter exactly as if you plugged a hardware network analyzer into a physical Ethernet switch.

6.3 NetAnim Visual Tracing (AnimationInterface)

To visualize node positions and packet transmissions in the graphical NetAnim animator:

#include "ns3/netanim-module.h"

// Instantiate after configuring NetDevices and IP addresses:
AnimationInterface anim("first-animation.xml");
anim.SetConstantPosition(nodes.Get(0), 10.0, 20.0);
anim.SetConstantPosition(nodes.Get(1), 50.0, 20.0);
anim.EnablePacketMetadata(true);

7. Looking Ahead: Wireless Modeling & WiFi 7/8

Once the 7-Step Recipe is mastered on wired point-to-point links, transitioning to wireless local area networks (WLAN) requires swapping only two helpers:

  • Replace PointToPointHelper with WifiHelper, WifiMacHelper, and YansWifiPhyHelper (or SpectrumWifiPhyHelper).

  • Add a MobilityHelper to define physical coordinates and RF propagation loss models.

  • For IEEE 802.11be (WiFi 7), configure Multi-Link Devices (AP MLD and non-AP MLD) across 2.4, 5, and 6 GHz bands using WIFI_STANDARD_80211be.

  • For IEEE 802.11bn (WiFi 8 UHR), research prototypes focus on Multi-AP Coordination (MAPC) to eliminate latency spikes.

These wireless paradigms will be explored in depth in Module 2 and Module 3.
