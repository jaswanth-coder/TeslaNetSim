Why C++ for Network Simulators?
 Network simulators like ns-3 must simulate millions of wireless packets, microsecond PHY timings, and multi-node queues without unexpected latency spikes. Unlike interpreted or garbage-collected languages (such as Python or Java) which introduce runtime memory sweeps and high per-object overhead, C++ provides:
  • Zero-Cost Abstractions: You only pay in CPU cycles and memory for what you actually use.
  • Deterministic Resource Management: Memory and hardware sockets are freed the exact nanosecond they go out of scope (RAII).
  • Bit-Level Serialization: Exact memory alignment for raw Ethernet, Wi-Fi 802.11, and IP byte streams.
This recap covers all C++ core concepts from the ground up, with dedicated code examples for every tricky concept.

10.4 Functions & The Three Parameter-Passing Conventions HARD CONCEPT

Understanding how data is passed into functions is the single most critical performance concept in C++. There are three conventions:

  • 1. Pass-by-Value (void Func(Packet p)): Makes a deep byte-by-byte copy. In a simulation processing 10,000,000 packets of 1,500 bytes each, this would waste 15 Gigabytes of memory bandwidth just duplicating bytes.
  • 2. Pass-by-Reference (void Func(Packet& p)): Passes an alias (memory address under the hood). No data is copied. The function can mutate the caller's original variable in place.
  • 3. Pass-by-Const-Reference (void Func(const Packet& p)): Passes an alias with zero copy overhead, but the compiler strictly enforces read-only access. This is the gold standard throughout ns-3 for inspecting packets, routing tables, and Wi-Fi headers.

Code Example: Direct Comparison of All Three Passing Conventions

#include <iostream>
#include <string>

// 1. Pass-by-Value: Modifies only a local duplicate
void ModifyValue(std::string str) {
    str += " [Copy Changed]";
}

// 2. Pass-by-Reference: Modifies caller's variable in place
void ModifyReference(std::string& str) {
    str += " [Original Changed]";
}

// 3. Pass-by-Const-Reference: Fast zero-copy, read-only
void PrintReadOnly(const std::string& str) {
    // str += " Error!"; <-- COMPILATION ERROR: Cannot modify const reference!
    std::cout << "Payload: " << str << " (Length: " << str.size() << " bytes)
";
}

int main() {
    std::string packetData = "Ethernet Frame #104";

    ModifyValue(packetData);
    std::cout << "After ModifyValue:     " << packetData << "
";

    ModifyReference(packetData);
    std::cout << "After ModifyReference: " << packetData << "
";

    PrintReadOnly(packetData);
    return 0;
}

10.5 Hardware Memory Model: Stack vs. Heap & Raw Pointers HARD CONCEPT

A C++ program's runtime memory is partitioned into two main regions:

  • The Stack: Fast memory managed automatically by the CPU stack pointer register (RSP). Variables declared inside functions live on the stack and are instantly reclaimed when the enclosing scope {} ends. Stack memory is limited (typically 8 MB on Linux).
  • The Heap: A large pool of system RAM for dynamically sized objects allocated at runtime via new (or malloc). The developer (or a smart pointer) is strictly responsible for freeing it via delete. Forgetting causes memory leaks; freeing twice causes segmentation faults.
Figure 10.2: Stack memory holding a raw pointer variable referencing a dynamically allocated heap block.

10.6 Object-Oriented Programming: Structs, Classes & Encapsulation

In C++, a struct and a class are nearly identical, with exactly one difference: members of a struct default to public, whereas members of a class default to private.

  • Encapsulation: Hide internal state variables behind private: and expose safe interfaces via public: methods.
  • Member Initializer Lists: Initialize fields directly before constructor execution starts: ClassName() : m_val(x) {}. This avoids double-initialization.
  • Const Member Methods: Methods marked const guarantee they do not modify any member variables: uint32_t GetSize() const;.

Code Example: Encapsulated Network Packet Header

#include <iostream>
#include <cstdint>

class PacketHeader {
private:
    uint16_t m_packetType;     // 16-bit EtherType or protocol ID
    uint32_t m_sequenceNumber; // 32-bit packet sequence number

public:
    // Constructor with Member Initializer List
    PacketHeader(uint16_t type, uint32_t seq)
        : m_packetType(type), m_sequenceNumber(seq) {
        std::cout << "[Header Constructed] Type=" << m_packetType << "
";
    }

    // Destructor
    ~PacketHeader() {
        // Automatically invoked when object leaves scope
    }

    // Const accessor (read-only inspection)
    uint16_t GetType() const { return m_packetType; }
    uint32_t GetSeq() const { return m_sequenceNumber; }

    // Mutator
    void IncrementSeq() { ++m_sequenceNumber; }
};

int main() {
    PacketHeader header(0x0800, 1001); // IPv4 EtherType
    header.IncrementSeq();
    std::cout << "Next Sequence: " << header.GetSeq() << "
";

}

10.7 Inheritance, Polymorphism & Virtual Function Tables (vtables) HARD CONCEPT

In network simulators, you need to treat diverse hardware devices (e.g. Ethernet cards, Wi-Fi 7 chips, LTE modems) uniformly through a common base interface: NetDevice. This is accomplished via polymorphism and virtual functions.

  • Pure Virtual Functions (virtual void Transmit() = 0;): Defines an interface contract. Classes containing pure virtual methods are Abstract Classes and cannot be instantiated directly.
  • The override Keyword: Instructs the compiler to verify that the derived class method exactly matches a virtual method in the base class.
  • Virtual Destructors: When deleting a derived object via a pointer to its base class (e.g., delete basePtr;), the base class destructor MUST be declared virtual ~Base() = default;. Without this, only the base destructor runs, leaking all derived resources!
Figure 10.3: The vtable dispatch mechanism allowing uniform base class pointers to invoke subclass-specific methods.

Code Example: Polymorphic Network Device Hierarchy

#include <iostream>
#include <memory>
#include <vector>
#include <string>
#include <cstdint>

// Abstract Base Class
class NetworkInterface {
protected:
    std::string m_name;
    uint32_t    m_mtu;

public:
    NetworkInterface(std::string name, uint32_t mtu)
        : m_name(std::move(name)), m_mtu(mtu) {}

    // Pure virtual method: subclasses MUST implement this!
    virtual void Transmit(const std::string& frame) = 0;

    // Essential: Virtual destructor ensures subclass destructors run properly
    virtual ~NetworkInterface() = default;

    std::string GetName() const { return m_name; }
};

// Derived Class: Wi-Fi Interface
class WifiInterface : public NetworkInterface {
private:
    double m_freqGhz;

public:
    WifiInterface(std::string name, uint32_t mtu, double freq)
        : NetworkInterface(std::move(name), mtu), m_freqGhz(freq) {}

    void Transmit(const std::string& frame) override {
        std::cout << "[Wi-Fi @ " << m_freqGhz << " GHz] Device " 
                  << m_name << " transmitting: " << frame << "
";
    }
};

int main() {
    // Polymorphism: Store derived objects in a collection of base pointers
    std::vector<std::unique_ptr<NetworkInterface>> devices;
    devices.push_back(std::make_unique<WifiInterface>("wlan0", 1500, 5.8));
    devices.push_back(std::make_unique<WifiInterface>("wlan1", 1500, 6.2)); // 6 GHz WiFi 6E/7

    for (const auto& dev : devices) {
        // Dynamic dispatch: calls WifiInterface::Transmit() at runtime!
        dev->Transmit("802.11 Probe Request");
    }

    return 0;
}

10.9 Modern C++ Idioms: `auto`, Lambdas & RAII

Modern C++ (C++11 through C++20) introduced three transformative features that make systems code clean, safe, and expressive:

  • Type Deduction (auto): The compiler automatically infers the variable type at compile time from its initializer without any runtime penalty.
  • Lambda Expressions ([captures](parameters) { body }): Anonymous inline callable objects. In ns-3, lambdas and callbacks are used to schedule simulation events at future timestamps.
  • RAII (Resource Acquisition Is Initialization): Objects acquire resources (memory, file handles, network sockets) in their constructor and guarantee release in their destructor when going out of scope.

Note for Beginners
 In standard C++, memory bugs (such as forgetting to call delete or deleting memory twice) cause silent memory exhaustion or catastrophic segmentation faults. In ns-3, you almost never write raw new or delete. Instead, ns-3 uses an elegant, high-performance smart pointer called Ptr<T> backed by intrusive reference counting. 11.1 The Core Problem: Why Raw Pointers Fail in Large Simulators

A single Wi-Fi simulation can generate, route, buffer, and destroy over 10,000,000 packets in a few minutes. Imagine managing that with raw C++ pointers (Packet* p = new Packet();):

  • The Memory Leak Disaster: If a packet is dropped by an intermediate router queue and the programmer forgets to call delete p;, your simulation will rapidly consume 16 GB of RAM and crash the computer.
  • The Dangling Pointer / Double-Free Crash: If both the wireless PHY layer and a tracing monitor attempt to delete p; at the same time, the program aborts instantly with a double free or corruption (fasttop) crash.
  • The Shared Ownership Reality: In real networks, multiple entities simultaneously "own" a packet—the transmission queue is holding it, the physical channel is transmitting it, and an analytical probe is calculating jitter on it. Who should be responsible for deleting it?

11.2 The Solution: Intrusive Reference Counting (The Library Book Analogy)

ns-3 solves shared ownership using Intrusive Reference Counting via the base class SimpleRefCount<T>:

The Library Book Analogy: Think of a shared library book with an internal checkout stamp counter. When the book is placed on the shelf, its counter is 1. When Borrower Alice checks it out, the counter increments to 2. When Borrower Bob also borrows it for a joint project, the counter becomes 3. When Alice returns it, the counter decrements to 2. When Bob returns it, the counter decrements to 1. When the library decides to retire the book and removes its own reference, the counter drops to 0. The exact instant the counter reaches 0, the book is safely recycled.

11.4 Step-by-Step Memory Lifecycle of an ns-3 Object

To see intrusive reference counting in action, let us trace four distinct time stages in code:

// Stage 1: Heap allocation
Ptr<Node> n1 = CreateObject<Node>(); // Heap allocation: m_count initialized to 1

// Stage 2: Assignment / Copying
Ptr<Node> n2 = n1;                  // Copy constructor: increments m_count to 2
NodeContainer container;
container.Add(n1);                  // Container stores its own Ptr: m_count increments to 3

// Stage 3: Scope Termination
{
    Ptr<Node> temp = n1;            // m_count increments to 4
}                                   // temp goes out of scope: destructor calls Unref() -> m_count drops back to 3

// Stage 4: Deletion
n2 = 0;                             // n2 reset: m_count drops to 2
n1 = 0;                             // n1 reset: m_count drops to 1
container.Clear();                  // container destroyed: m_count drops to 0 -> delete this!

11.5 Canonical C++ Script: Demonstrating SimpleRefCount & Ptr<T>

Below is a minimal, educational C++ script showing how you can create your own reference-counted class in ns-3:

#include "ns3/core-module.h"
#include <iostream>

using namespace ns3;

// Inherit from SimpleRefCount to make our class reference-counted!
class MyBuffer : public SimpleRefCount<MyBuffer>
{
public:
  MyBuffer (uint32_t size) : m_size (size) {
    std::cout << "[CONSTRUCTOR] Allocating MyBuffer of size: " << m_size << " bytes\n";
  }
  ~MyBuffer () {
    std::cout << "[DESTRUCTOR] Deallocating MyBuffer of size: " << m_size << " bytes automatically!\n";
  }
  void PrintInfo () const {
    std::cout << "  -> Buffer holding " << m_size << " bytes\n";
  }
private:
  uint32_t m_size;
};

void ProcessBuffer (Ptr<MyBuffer> buf)
{
  std::cout << "Inside ProcessBuffer: Reference count incremented temporarily\n";
  buf->PrintInfo ();
}

int main ()
{
  std::cout << "--- STEP 1: Creating object on Heap via Create<T> ---\n";
  Ptr<MyBuffer> p1 = Create<MyBuffer> (1024); // m_count starts at 1
  
  std::cout << "--- STEP 2: Creating a second reference p2 ---\n";
  Ptr<MyBuffer> p2 = p1; // Copy constructor increments m_count to 2
  
  std::cout << "--- STEP 3: Passing p2 by value to a function ---\n";
  ProcessBuffer (p2); // Copies Ptr, m_count becomes 3 inside function, drops back to 2 upon return
  
  std::cout << "--- STEP 4: Resetting p1 ---\n";
  p1 = 0; // p1 drops reference, m_count drops to 1. Buffer NOT deleted yet!
  
  std::cout << "--- STEP 5: Resetting p2 (The last remaining reference) ---\n";
  p2 = 0; // m_count drops to 0 -> Destructor automatically called here!
  
  std::cout << "--- End of main program ---\n";
  return 0;
}

11.7 Student Best Practices & The Circular Reference Trap

Warning: Circular Reference Deadlock
 If Object A holds Ptr<B> and Object B holds Ptr<A>, neither object can ever reach m_count == 0. Even if all external pointers are destroyed, they will keep each other alive forever, causing a permanent memory leak. In ns-3, break circular references by having one side store a raw pointer (T*) or by breaking the link during DoDispose().
Performance Pro-Tip: Pass by Const Reference
 Passing Ptr<T> by value (void Foo (Ptr<Node> n)) causes atomic increment and decrement of m_count. For high-speed simulations processing millions of packets, always pass by const reference: void Foo (const Ptr<Node>& n). This avoids touching m_count completely while maintaining safety!

#include "ns3/core-module.h"
#include "ns3/network-module.h"
#include <iostream>

using namespace ns3;

// 1. A Custom Network Component that can be aggregated onto a Node
class BatteryComponent : public Object
{
public:
  static TypeId GetTypeId (void) {
    static TypeId tid = TypeId ("ns3::BatteryComponent")
      .SetParent<Object> ()
      .AddConstructor<BatteryComponent> ();
    return tid;
  }
  BatteryComponent () : m_joules (1000.0) {}

  void DrainBattery (double amount) {
    m_joules -= amount;
    std::cout << "  [Battery] Drained " << amount << " J. Remaining: " << m_joules << " J\n";
    if (m_joules <= 500.0 && !m_lowBatteryCallback.IsNull ()) {
      m_lowBatteryCallback (m_joules); // Invoke callback!
    }
  }

  void SetLowBatteryCallback (Callback<void, double> cb) {
    m_lowBatteryCallback = cb;
  }

private:
  double m_joules;
  Callback<void, double> m_lowBatteryCallback;
};

// 2. An Observer Class that handles the event
class PowerManager
{
public:
  void OnLowBatteryWarning (double remainingJoules) {
    std::cout << "  [PowerManager ALERT] Low battery warning! Switching to Power-Save Mode. Level = " 
              << remainingJoules << " J at t = " << Simulator::Now ().GetSeconds () << "s\n";
  }
};

int main ()
{
  std::cout << "=== 1. Creating Node and Aggregating Component ===\n";
  Ptr<Node> node = CreateObject<Node> ();
  Ptr<BatteryComponent> battery = CreateObject<BatteryComponent> ();
  
  // Aggregate battery into the Node
  node->AggregateObject (battery);

  std::cout << "=== 2. Binding Member Method Callback ===\n";
  PowerManager manager;
  
  // Query battery back from Node using GetObject<T>()!
  Ptr<BatteryComponent> queriedBattery = node->GetObject<BatteryComponent> ();
  NS_ASSERT (queriedBattery != 0); // Verify component was found

  // Hook PowerManager::OnLowBatteryWarning as the callback target
  queriedBattery->SetLowBatteryCallback (
    MakeCallback (&PowerManager::OnLowBatteryWarning, &manager)
  );

  std::cout << "=== 3. Scheduling Discrete Simulation Events ===\n";
  // Schedule battery drains across simulation time
  Simulator::Schedule (Seconds (1.0), &BatteryComponent::DrainBattery, queriedBattery, 300.0);
  Simulator::Schedule (Seconds (2.5), &BatteryComponent::DrainBattery, queriedBattery, 250.0); // Triggers callback!
  Simulator::Schedule (Seconds (4.0), &BatteryComponent::DrainBattery, queriedBattery, 100.0);

  std::cout << "=== 4. Running Simulation Scheduler ===\n";
  Simulator::Run ();
  Simulator::Destroy ();
  std::cout << "Simulation Finished Successfully!\n";
  return 0;
}

1.1 Discrete-Event Simulation (DES) vs. Real-World Wall-Clock Time

In everyday programming (such as web servers or game engines), time advances continuously according to the CPU wall-clock stopwatch ($\Delta t = 16.6\text{ ms}$ for 60 frames per second). In contrast, ns-3 is a Discrete-Event Simulator (DES).

⏱️ Visual Flow: Discrete Event Priority Queue & Clock Leaps

Figure 1.1: The event priority queue calendar. When the calendar executes $t=2.002\text{s}$, it immediately leaps forward to the next scheduled event without wasting wall-clock CPU instructions.

  • The Event Calendar: A priority queue $Q$ sorted strictly by timestamp $t$.
  • Zero Idle Latency: If no events are scheduled between $2.002\text{s}$ and $10.0\text{s}$, the simulator advances virtual time instantaneously.

2.1 The Core Network Abstraction Trifecta: Node, NetDevice & Channel

In physical networking, communication requires three physical entities: a computing computer, a network card interface (NIC), and an interconnecting cable or wireless medium. In ns-3, these map directly to three primary C++ abstractions:

  • Logical Host (Ptr<Node>): Represents a network host, router, switch, or mobile station. Crucially, a Node begins as a completely "blank slate" (no NICs, no IP stack, no apps). Layers must be explicitly attached via the object aggregation system.

  • Physical Medium (Ptr<Channel>): Represents the transmission medium (fiber optics, coaxial cable, or wireless radio propagation environment). A NetDevice plugs into a Channel to propagate signals.

4.5 Queues, Bufferbloat & Active Queue Management (AQM)

Whenever packets arrive faster than a link's transmission rate, they accumulate in a buffer queue inside the NetDevice.

  • DropTailQueue: Standard First-In-First-Out (FIFO) buffer. When the queue reaches capacity (e.g. 100 packets), all new incoming packets are dropped at the tail. This can cause TCP global synchronization.
  • CoDel (Controlled Delay): Modern Active Queue Management (AQM) that monitors packet queuing delay. If packets sit in the queue longer than 5 ms, CoDel drops packets proactively to signal TCP senders to back off, eliminating bufferbloat.
// Customizing the transmission queue size on a PointToPoint link:
pointToPoint.SetQueue ("ns3::DropTailQueue<Packet>", "MaxSize", QueueSizeValue (QueueSize ("50p")));

8.1 The C++ OpenGymInterface Architecture

In ns3-gym, the C++ simulation exposes a virtual OpenAI Gym environment by subclassing OpenGymInterface. The C++ class defines:

  1. Observation Space: The state variables observable by the ML model (e.g. current SNR, packet loss rate, queue buffer backlog).

9.1 Python Gymnasium & PyTorch Deep Q-Network (DQN) Agent

With the C++ simulation acting as an environment server, the Python script connects via gym.make('ns3-v0') and trains a Deep Q-Network (DQN) agent with experience replay to maximize throughput while minimizing queue bufferbloat.

Full Canonical Python Code (train_ns3_dqn.py):

import gymnasium as gym
import ns3gym
from ns3gym import ns3env
import torch
import torch.nn as nn
import torch.optim as optim
import random
import numpy as np
from collections import deque

# STEP 1: Deep Q-Network Architecture
class QNetwork(nn.Module):
    def __init__(self, state_dim, action_dim):
        super(QNetwork, self).__init__()
        self.fc = nn.Sequential(
            nn.Linear(state_dim, 64),
            nn.ReLU(),
            nn.Linear(64, 64),
            nn.ReLU(),
            nn.Linear(64, action_dim)
        )

    def forward(self, x):
        return self.fc(x)

# STEP 2: Replay Buffer for Off-Policy RL
class ReplayBuffer:
    def __init__(self, capacity=10000):
        self.buffer = deque(maxlen=capacity)

    def push(self, state, action, reward, next_state, done):
        self.buffer.append((state, action, reward, next_state, done))

    def sample(self, batch_size):
        states, actions, rewards, next_states, dones = zip(*random.sample(self.buffer, batch_size))
        return (torch.FloatTensor(np.array(states)),
                torch.LongTensor(actions),
                torch.FloatTensor(rewards),
                torch.FloatTensor(np.array(next_states)),
                torch.FloatTensor(dones))

    def __len__(self):
        return len(self.buffer)

# STEP 3: Main Training Loop
def train():
    port = 5555
    sim_time = 60 # seconds
    step_time = 0.1 # 100 ms step duration

    # Initialize ns-3 gym environment
    env = ns3env.Ns3Env(port=port, stepTime=step_time, startSim=True, simSeed=42)
    state_dim = env.observation_space.shape[0] # 2 features
    action_dim = env.action_space.n           # 4 discrete rates

    policy_net = QNetwork(state_dim, action_dim)
    target_net = QNetwork(state_dim, action_dim)
    target_net.load_state_dict(policy_net.state_dict())

    optimizer = optim.Adam(policy_net.parameters(), lr=1e-3)
    memory = ReplayBuffer(10000)

    gamma = 0.99
    epsilon = 1.0
    epsilon_min = 0.05
    epsilon_decay = 0.995
    batch_size = 32

    num_episodes = 20
    print("🚀 Starting Deep Reinforcement Learning Training with ns-3...")

    for episode in range(num_episodes):
        state = env.reset()
        total_reward = 0.0
        done = False

        while not done:
            # Epsilon-greedy action selection
            if random.random() < epsilon:
                action = env.action_space.sample()
            else:
                with torch.no_grad():
                    state_t = torch.FloatTensor(state).unsqueeze(0)
                    action = policy_net(state_t).argmax().item()

            # Execute action inside ns-3 simulation!
            next_state, reward, done, info = env.step(action)
            memory.push(state, action, reward, next_state, done)

            state = next_state
            total_reward += reward

            # Train Deep Q-Network
            if len(memory) >= batch_size:
                states, actions, rewards, next_states, dones = memory.sample(batch_size)

                q_values = policy_net(states).gather(1, actions.unsqueeze(1)).squeeze(1)
                with torch.no_grad():
                    max_next_q = target_net(next_states).max(1)[0]
                    target_q = rewards + (1 - dones) * gamma * max_next_q

                loss = nn.MSELoss()(q_values, target_q)
                optimizer.zero_grad()
                loss.backward()
                optimizer.step()

        # Decay exploration rate
        epsilon = max(epsilon_min, epsilon * epsilon_decay)
        # Update target network
        if episode % 2 == 0:
            target_net.load_state_dict(policy_net.state_dict())

        print(f"Episode {episode + 1}/{num_episodes} - Total Reward: {total_reward:.2f} - Epsilon: {epsilon:.3f}")

    print("🎉 Training Complete! Model converged successfully.")
    torch.save(policy_net.state_dict(), "ns3_dqn_policy.pth")
    env.close()

if __name__ == "__main__":
    train()

12.1 Path Loss Physics & Node Kinematics

In wired Ethernet, a signal does not degrade whether a cable is 1 meter or 10 meters long. In wireless networking, received power attenuates exponentially with distance according to the Friis Transmission Formula:

\[ P_{\text{rx}}(d) = P_{\text{tx}} \cdot G_{\text{tx}} \cdot G_{\text{rx}} \cdot \left(\frac{\lambda}{4\pi d}\right)^2 \]

As a mobile client walks away from the Access Point, the received signal power drops below the receiver sensitivity threshold (e.g. $-82\text{ dBm}$), leading to bit errors, packet retries, and eventual disconnect.

13.1 Enhanced Distributed Channel Access (EDCA) Priority

In early Wi-Fi (802.11b), all packets competed equally. If someone was downloading a large torrent file, video conferences stuttered. IEEE 802.11e / 802.11n / 802.11ac / 802.11ax QoS solves this by mapping packets into four Access Categories (ACs):

  • AC_VO (Voice): Smallest contention window ($CW_{\min}=3, CW_{\max}=7$), smallest AIFS ($2\text{ slots}$). Transmits first with near-zero latency.
  • AC_VI (Video): Medium-high priority ($CW_{\min}=7, CW_{\max}=15$).
  • AC_BE (Best Effort): Standard priority ($CW_{\min}=15, CW_{\max}=1023$).
  • AC_BK (Background): Lowest priority ($CW_{\min}=15, CW_{\max}=1023$, large AIFS). Defers channel access whenever Voice or Video packets are queued.

double
CustomTwoSlopeLossModel::DoCalcRxPower (double txPowerDbm,
                                       Ptr<MobilityModel> a,
                                       Ptr<MobilityModel> b) const
{
  double dist = a->GetDistanceFrom (b);
  if (dist <= 0.0) dist = 0.001; // Avoid division by zero

  double lossDb = 0.0;
  if (dist <= m_breakDistance) {
    // Stage 1: Standard Line-of-sight free space loss
    lossDb = 10.0 * m_exponent1 * std::log10 (dist);
  } else {
    // Stage 2: Steeper path loss slope due to multi-path ground bounce and obstacles
    double lossAtBreak = 10.0 * m_exponent1 * std::log10 (m_breakDistance);
    lossDb = lossAtBreak + 10.0 * m_exponent2 * std::log10 (dist / m_breakDistance);
  }

  return txPowerDbm - lossDb;
}

  return 0; // Deterministic model without random fading streams
}

CustomThresholdRateManager::CustomThresholdRateManager ()
  : m_upThreshold (10)
{
}

CustomThresholdRateManager::~CustomThresholdRateManager () {}

WifiRemoteStation*
CustomThresholdRateManager::DoCreateStation (void) const
{
  CustomStationState *station = new CustomStationState ();
  station->m_consecutiveSuccess = 0;
  station->m_currentRateIndex = 0; // Start at lowest safe MCS rate
  return station;
}

WifiTxVector
CustomThresholdRateManager::DoGetDataTxVector (WifiRemoteStation *st, uint16_t allowedWidth)
{
  CustomStationState *station = static_cast<CustomStationState*> (st);
  WifiMode mode = GetSupported (station, station->m_currentRateIndex);

  return WifiTxVector (mode,
                       GetDefaultTxPowerLevel (),
                       GetPreambleForTransmission (GetStandard (), mode),
                       800, // 800ns standard guard interval
                       1,   // 1 spatial stream (SISO)
                       1,
                       20,  // 20 MHz channel width
                       false,
                       false);
}

void
CustomThresholdRateManager::DoReportRxOk (WifiRemoteStation *st, double rxSnr, WifiMode txMode)
{
  CustomStationState *station = static_cast<CustomStationState*> (st);
  station->m_consecutiveSuccess++;

  // If 10 consecutive packets succeed, shift up to faster MCS!
  if (station->m_consecutiveSuccess >= m_upThreshold) {
    if (station->m_currentRateIndex + 1 < GetNSupported (station)) {
      station->m_currentRateIndex++;
    }
    station->m_consecutiveSuccess = 0;
  }
}

void
CustomThresholdRateManager::DoReportDataFailed (WifiRemoteStation *st)
{
  CustomStationState *station = static_cast<CustomStationState*> (st);
  station->m_consecutiveSuccess = 0;

  // On packet drop, immediately fall back to lowest robust rate
  if (station->m_currentRateIndex > 0) {
    station->m_currentRateIndex--;
  }
}

In modern Linux and ns-3, queueing is handled by the Traffic Control Layer (between Layer 2 and Layer 3). To implement custom queue disciplines (like CoDel, RED, or Token Bucket Shaping):

  • Target Directory: src/traffic-control/model/

A primer breaking down the internals of ns-3 discrete event simulation, the Node state graph, and the dual-queue architecture of the Traffic Control Layer.

Core Architectural Concepts to Master

  • 1. Node as State Graph: A Node has no pre-defined physical edges. Instead, it aggregates:
    • A collection of NetDevice objects (analogous to physical NIC ports and driver queues).
    • A list of Application objects (producers and consumers of packet traffic).
    • A list of protocol handlers: Ipv4L3Protocol, ArpL3Protocol, TcpL4Protocol, UdpL4Protocol.
  • 2. The Dual-Queue Architecture (Traffic Control vs. NetDevice):

    In modern ns-3, there are TWO distinct queues before a packet reaches the wire/air:

    1. The Queueing Discipline (Qdisc) inside the TrafficControlLayer (e.g. FqCoDel, PFifoFast, RedQueueDisc).
    2. The NetDevice's own internal hardware queue.

    The Golden Rule: The TrafficControlLayer checks if the NetDevice queue has space before pushing. Therefore, in standard configurations, all queuing drops occur at the Traffic Control Layer; the NetDevice queue itself never drops packets!

  • 3. Lazy Packet Payload Mechanics: A Packet in ns-3 allocates memory lazily. As long as applications do not explicitly fill or parse payload bytes, the packet size is represented as an integer tag, drastically speeding up simulation time and conserving RAM.
